「让某个程序开机就跑」在 Linux 桌面上有六条互不等价的链路，它们在启动时机、存活范围、失败后行为、运行环境和可查询性上各不相同。先把这五个维度摆出来，再判断某类程序该落在哪条上，最后用 Arch + niri 的一次整理作为实例。本文由 Qoder 撰写。

<!--more-->

## 比较链路用的五个维度

- 启动时机：开机、登录、图形会话建立，还是第一次被访问。
- 存活范围：跨会话常驻，还是随会话结束而退出。
- 失败后的行为：有没有重启策略，崩溃是否会被发现。
- 运行环境：以哪个用户、哪一组环境变量启动（`WAYLAND_DISPLAY`、`DBUS_SESSION_BUS_ADDRESS` 是否在）。
- 可查询性：崩溃后能不能用一个稳定的名字去 `status`、去取日志。

多数「自启动没生效」和「自启动杀不掉」的问题，都是把这五维不匹配的程序放错了链路。

## 六条链路

### 1. 系统级 systemd 单元

`WantedBy=multi-user.target`，root 身份，开机即起，与任何人登录无关。适合设备与内核相关的守护进程（`udisks2`、`bluetooth`、`cups`）。桌面程序一般不属于这里——它需要用户身份和用户级环境变量。

### 2. 登录器与 PAM 阶段的脚本

`pam_env`、`~/.xprofile`、`~/.xinitrc.d/`、显示管理器的会话前后脚本（SDDM 的 `SessionSetup`）。这条链路只覆盖经过它的会话类型：X11 会话会读 `~/.xprofile`，直接启动合成器的 Wayland 会话不会。用错了就是「终端里启动正常、从登录界面进去没跑」。

### 3. systemd user 单元

`systemctl --user enable`，由 `user@<uid>.service` 在第一次登录时拉起。它有两种归属：

- `WantedBy=default.target`：随登录启动，退出登录后仍活到 `user@` 停止；`Linger=yes` 时甚至不需要登录。
- `PartOf=graphical-session.target`（或由 autostart 生成器加上）：严格跟着图形会话生死。

这条链路是唯一提供 `Restart=`、`ExecCondition=`、资源限制和 cgroup 归属的，也是唯一有稳定单元名的。

### 4. socket 与 D-Bus 激活

`.socket` 单元（`pipewire.socket`、`gnome-keyring-daemon.socket`、`gpg-agent.socket`）和 session bus 上的服务文件。程序不常驻，第一次访问才起，端口由 systemd 或总线持有。上游现在普遍偏好这种：能不占内存就不占。代价是启动时序不由你控制，且拿不到「已经在跑」这个前提。

### 5. XDG autostart

`/etc/xdg/autostart/*.desktop`（包安装的）与 `~/.config/autostart/*.desktop`（用户覆盖）。规范上这是桌面环境要实现的行为，但本机这套（systemd 262）里它已经可以完全交给 systemd：`systemd-xdg-autostart-generator` 会为每个条目生成一个 user 单元，由会话用 `xdg-desktop-autostart.target` 拉起。生成规则里几个值得知道的键：

| `.desktop` 里的键 | 生成结果 |
| --- | --- |
| `Hidden=`、`X-systemd-skip=` | 置 true 则不生成单元 |
| `TryExec=` | 程序不存在或不可执行则不生成 |
| `OnlyShowIn=`、`NotShowIn=` | 变成 `ExecCondition=`，用 `systemd-xdg-autostart-condition` 判断 |
| `X-GNOME-Autostart-Phase=` | 设了任何值都不生成（这类条目要由完整桌面环境自己处理） |

所以只想关掉某个包的自启动、又不愿卸载它，正规做法是在 `~/.config/autostart/` 放同名文件写 `Hidden=true`，而不是删系统目录里的文件。

### 6. 合成器或窗口管理器的启动配置

niri 的 `spawn-at-startup` / `spawn-sh-at-startup`、Hyprland 的 `exec` / `exec-once`、sway 的 `exec`、i3 的 `exec`、Openbox 的 `autostart`。特点是最贴近会话：它一定在显示环境就绪之后执行，配置和窗口规则在同一个文件里；缺点也在这里——多数实现只是 fork 一个进程，剩下四个维度都是默认值。

还有一条经常被人当成第七种：`~/.zshrc` / `~/.profile`。它只在交互 shell 里执行，从启动器、D-Bus 或会话直接拉起的图形程序根本不经过它，不该用它承载任何服务。

## 判断该落在哪条链路

四个问题按顺序问：

1. 需要用户身份吗？不需要 → 系统单元。
2. 需要图形会话吗（要用 `WAYLAND_DISPLAY` / `DISPLAY`）？不需要 → user 单元或 socket 激活，别放进 WM 配置。需要 → 只有 XDG autostart 和 WM 配置天然满足；用 user 单元就得让它依赖 `graphical-session.target`。
3. 崩了必须回来吗？必须 → systemd 单元 + `Restart=`。瞬时 scope 和 `exec` 都不提供这个。
4. 能按需拉起吗？能 → 交给 socket 或 D-Bus 激活，不要常驻。

加一条硬约束：任何持有独占资源（socket、端口、设备节点、总线名）的程序只能由一种机制启动。两种机制并存时，后起的那个必然失败，而失败信息常常被重启策略掩盖。

按程序类型的常见归属：

| 程序类型 | 合适的链路 |
| --- | --- |
| 音频、密钥环、代理这类有套接字的守护 | socket 激活，或包自带的 user 单元 |
| 崩溃不可接受的常驻服务（同步、代理、输入法之外的后端） | user 单元 + `Restart=` |
| 状态栏、壁纸、通知、OSD 这类图形会话组件 | XDG autostart；需要重启策略时改 user 单元 |
| 上游只提供 `.desktop` 的程序 | XDG autostart |
| 依赖 WM 自身接口的一次性动作（键位、规则、截图脚本） | WM 启动配置 |
| 会话级环境变量 | 会话包装脚本或 `systemctl --user set-environment`，不是 `spawn` 一个 shell |

## 实例：niri 下这几条链路怎么接起来

niri 作为会话启动时，`/usr/bin/niri-session` 先做四件事，再把合成器本身交给 systemd：

```sh
systemctl --user reset-failed
systemctl --user import-environment
dbus-update-activation-environment --all
systemctl --user --wait start niri.service
# 会话结束后
systemctl --user start --job-mode=replace-irreversibly niri-shutdown.target
systemctl --user unset-environment WAYLAND_DISPLAY DISPLAY XDG_SESSION_TYPE XDG_CURRENT_DESKTOP NIRI_SOCKET
```

`niri.service` 的片段把会话目标和其他链路绑在一起：

```ini
# /usr/lib/systemd/user/niri.service
[Unit]
BindsTo=graphical-session.target
Before=graphical-session.target
Wants=graphical-session-pre.target
After=graphical-session-pre.target

Wants=xdg-desktop-autostart.target
Before=xdg-desktop-autostart.target

[Service]
Slice=session.slice
Type=notify
ExecStart=niri --session
```

也就是说，niri 把 XDG autostart 委托给了 systemd 的生成器，自己的 `startup.kdl` 只补它必须亲自做的部分（合成器内部行为、依赖 niri socket 的脚本）。`startup.kdl` 开头的注释就是这个意思：

```
// Note that running niri as a session supports xdg-desktop-autostart,
// which may be more convenient to use.
```

`~/.config/autostart/` 里留下的三个历史条目都已经写了 `Hidden=true`，生成器不再为它们产出单元，`systemctl --user list-units --all | grep picom` 是空的——这就是那条表格里 `Hidden=` 的效果，也是不用卸载包就能关掉自启动的验证方式。

输入法走的是第五条链路，包只给了 `.desktop`：

```
# /run/user/1000/systemd/generator.late/app-org.fcitx.Fcitx5@autostart.service
# Automatically generated by systemd-xdg-autostart-generator
SourcePath=/etc/xdg/autostart/org.fcitx.Fcitx5.desktop
PartOf=graphical-session.target
After=graphical-session.target

[Service]
Type=exec
ExitType=cgroup
ExecStart=:/usr/bin/fcitx5
Restart=no
TimeoutStopSec=5s
Slice=app.slice
```

值得注意的是它同样是 unit：`PartOf=graphical-session.target` 保证退出会话时收掉，`Restart=no` 说明 autostart 也不负责复活，`ExecStart=` 前的冒号表示 exec 失败会被忽略。也就是说这条链路比 WM 配置多了生命周期，但并没有多重试。

## `spawn-at-startup` 起出来的进程是什么形态

niri 的实现不是简单 fork：它把每个子进程放进一个 systemd 瞬时 scope，通过 session bus 调 `StartTransientUnit`：

```rust
// src/utils/spawning.rs
let mut scope_name = String::from("app-niri-");
// ……非 [A-Za-z0-9:_.] 的字符按 \xNN 转义（注释说明这套转义抄自 systemd）
let _ = write!(scope_name, "-{child_pid}.scope");

let properties: &[_] = &[
    ("PIDs", Value::new(pids)),
    ("CollectMode", Value::new("inactive-or-failed")),
];
proxy.call("StartTransientUnit", &(scope_name, "fail", properties, aux))
```

代码注释写的动机是把子进程和合成器分开，避免某个客户端触发 OOM 时把 niri 一起带走；同时也提到一个 systemd 竞态——子进程恰好立刻退出时可能留下一个空的瞬时单元，所以它用双 fork 和管道拿到孙进程 PID 后再建 scope。

实际会话里看到的就是这些名字（节选）：

```
app-niri-awww\x2ddaemon-1874.scope
app-niri-copyq-1872.scope
app-niri-mihomo-1864.scope
app-niri-niri_auto_blur_bg.sh-1890.scope
app-niri-polkit\x2dgnome\x2dauthentication\x2dagent\x2d1-1869.scope
app-niri-shikane-1859.scope
app-niri-swayosd\x2dserver-1898.scope
app-niri-waypaper.sh-1885.scope
app-niri-sh-1876.scope          ← spawn-sh-at-startup 起的 shell
```

对到前面五个维度上：

- scope 没有 `Restart=`，进程挂了不会复活。
- 单元名带 PID，每次会话都是新名字，无法用固定单元名去 `status` 或 `restart`。
- 生命周期靠会话本身，退出 niri 时一并收掉。
- 环境变量继承自合成器进程，这一点比 user 单元可靠。

`systemctl --user show app-niri-copyq-1872.scope -p Slice` 显示它在 `app.slice` 下，与 autostart 生成的单元同一片。

## 三个具体的取舍

### 需要复活的一律走 user 单元

状态栏属于「崩了必须有回来」的程序，而 scope 不提供重启，所以配置里那行是注释掉的：

```
// 任务栏 经常崩溃，使用systemd开启
//spawn-at-startup "waybar"
```

改为 enable 过的 user 单元后，`systemctl --user status waybar` 能直接看到退出码和日志。

### 持有独占 socket 的程序不能两种机制并存

`ydotool` 包自带 user 级单元：

```ini
# /usr/lib/systemd/user/ydotool.service
[Service]
Type=simple
Restart=always
ExecStart=/usr/bin/ydotoold
TimeoutSec=180

[Install]
WantedBy=default.target
```

往 `startup.kdl` 里加一行 `spawn-at-startup "ydotoold"` 之后，两边都在启动同一个程序，而 `ydotoold` 在 `$XDG_RUNTIME_DIR` 上独占一个 socket：

```
● ydotool.service - Starts ydotoold service
    Active: failed
    NRestarts=5
ydotoold[90375]: Socket path: /run/user/1000/.ydotool_socket
ydotoold[90375]: error: Another ydotoold is running with the same socket.
```

先起来的是那个没有重启策略的 scope，它合法持有 socket；带 `Restart=always` 的单元于是永远失败，`NRestarts` 一直涨，日志里看到的只是「另一个实例在跑」这个结果而不是原因。撤掉 `startup.kdl` 那行、让 scope 里的实例随会话退出，单元才接管：

```
ydotool.service    loaded active running   Starts ydotoold service
srw------- 1 zhh7ce wheel 0 /run/user/1000/.ydotool_socket
```

顺带确认了非 root 跑 `ydotoold` 的前置条件，三者缺一即启动失败：`/dev/uinput` 的属组与 ACL（`crw-rw----+ 1 root input`、`getfacl` 里的 `user:zhh7ce:rw-`）、用户在 `input` 组、以及 `/usr/lib/udev/rules.d/90-ydotool-uinput.rules`。

### 会话环境变量要交给会话，不是交给某一行 spawn

状态栏之外，屏幕共享/录屏相关的一组变量也需要在总线里可见，配置里对应两行：

```
spawn-sh-at-startup "dbus-update-activation-environment --systemd WAYLAND_DISPLAY XDG_CURRENT_DESKTOP=niri & /usr/lib/xdg-desktop-portal-gnome"
spawn-sh-at-startup "systemctl --user set-environment XDG_SESSION_CLASS=user"
```

第一行把 Wayland 变量写进 D-Bus 的激活环境，否则由总线拉起的程序（portal、文件管理器）拿不到 `WAYLAND_DISPLAY`。走 `niri-session` 进入会话时，包装脚本里的 `import-environment` 和 `dbus-update-activation-environment --all` 已经做过一次；直接以 `niri` 命令启动合成器（不经包装脚本）时，这一步必须自己补。第四、五条链路之间不会自动同步环境，这是「同一个服务在终端里好好的、被总线拉起就找不到显示」这类问题的根源。

现在的分工因此是：只在图形会话里有意义、且崩溃可接受的东西留在 `startup.kdl`（polkit 认证代理、壁纸守护及其 overview 实例、两个自定义脚本、`swayidle`、`swayosd-server`、`copyq`、`mihomo`）；需要重启策略或稳定单元名的走 user 单元（`waybar`、`ydotool`、`syncthing`、`wireplumber`、`remote-input-board`、`xdg-user-dirs`）；上游只给 `.desktop` 的留在 autostart（`fcitx5`）。

## 排查命令

```bash
systemctl --user list-units --all | grep -E 'app-niri|@autostart'   # 谁以什么形态在跑
systemctl --user list-unit-files --state=enabled
systemctl --user list-dependencies graphical-session.target          # 会话建立后一共挂了哪些东西
systemctl --user cat <unit>                                         # 单元内容，含包自带与生成器产物
ls /run/user/1000/systemd/generator.late/                            # autostart 生成的单元
ls /etc/xdg/autostart/ ~/.config/autostart/
journalctl --user -u <unit> --no-pager | tail -20
loginctl show-user "$USER" -p Linger                                 # 无会话时是否保留 user@.service
```

## 后记

选择顺序大致是：程序自己给了 user 单元或 socket 就用它；上游只给了 `.desktop` 就留在 autostart（它已经是一个 unit，比想象中可控）；只有「只在图形会话里有意义、崩了无所谓」的才写进 WM 的 spawn 配置；shell rc 不承担服务。

两个容易反复踩的点：同一程序混用两种机制，尤其是其中一种带 `Restart=always` 时，会把「已经有合法实例」伪装成一串重启失败；以及各链路的环境变量互不相通，总线与 socket 拉起的程序拿到的是激活环境里那份，不是当前终端那份。

`loginctl enable-linger` 只在「没有图形会话也要跑」时才需要。桌面自启动不依赖它，会话型程序随 `user@` 一起生灭通常正是想要的行为。
